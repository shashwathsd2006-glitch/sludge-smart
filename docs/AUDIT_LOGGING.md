# Audit logging

The audit trail is append-only and written in the same database transaction as the business change it describes.

## Record fields

| Field | Meaning |
|---|---|
| `id` | Sequential audit record ID. |
| `timestamp` | UTC ISO-8601 with milliseconds. |
| `actor_user_id` | Authenticated user ID; `NULL` for anonymous activity. |
| `actor_username` | Username snapshot, or `anonymous`. |
| `action` | `CREATE`, `UPDATE`, `DELETE`, `LOGIN`, `LOGIN_FAILED`, `LOGOUT`, `APPROVAL`, `PERMISSION_DENIED`, `PASSWORD_CHANGE`, `PASSWORD_RESET`. |
| `resource` | Table name or `auth`; permission code for shadow denials. |
| `record_id` | Affected record ID as text, when applicable. |
| `before_values` | JSON snapshot before an update/delete. |
| `after_values` | JSON snapshot after a create/update. |
| `changed_fields` | JSON list of changed keys. |
| `outcome` | `success` or `failure`. |
| `detail` | Short human-readable context (never credentials). |
| `ip_address`, `user_agent` | Request metadata, treated as untrusted. |
| `request_id` | Correlation ID from `X-Request-ID` or generated by middleware. |

## What is recorded

- Legacy POST/PATCH/PUT/DELETE operations on all six original tables, including PATCH for generation, characterisation, handling and disposals: actor, action, resource, record ID, before/after values and changed fields.
- `PATCH /api/compliance/{id}` that changes status to `Compliant` is logged as `APPROVAL`; other changes are `UPDATE`.
- Login success, login failure (including rate limiting) and logout.
- `PASSWORD_CHANGE` for successful self-service changes and for rejected attempts (wrong current password or reuse), with `resource=auth`, the user as actor and a non-credential `detail`.
- `PASSWORD_RESET` for administrator resets, with `resource=users`, the administrator as actor, the target user ID as `record_id`, and only non-credential flags in `after_values`.
- Permission denials in shadow mode, with the attempted permission code as `resource`.
- Anonymous legacy writes are attributed to `anonymous`; they are never attributed to a registered user unless a valid Bearer token was supplied.

## Protection and redaction

- Keys containing `password`, `token`, `secret`, `credential` or `hash` are replaced with `[REDACTED]` in all JSON snapshots. Raw tokens and password hashes are never written.
- SQLite triggers `audit_logs_no_update` and `audit_logs_no_delete` abort any UPDATE or DELETE on the table. No API route exposes audit modification or deletion.
- `GET /api/audit` requires `audit:read` (administrator or EHS reviewer) and supports filters `action`, `resource`, `actor_user_id`, `from_ts`, `to_ts`, plus `limit`/`offset`. Filter values are checked against fixed allowlists before being used in a WHERE clause.

## Correlation IDs

The HTTP middleware accepts a trusted `X-Request-ID` (alphanumeric, `-`/`_`, max 64 characters) or creates one with `uuid4().hex`. It is echoed in the response header and stored with every audit row created during that request.

## Limitations

- Audit rows are never pruned in Phase 1; define a retention/archival policy before long-term production use.
- Request metadata can be spoofed by clients; it is informational only.
- Audit writes use the same process-local SQLite transaction as the business operation; distributed deployments need a shared transactional store.
